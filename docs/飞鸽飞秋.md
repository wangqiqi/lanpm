## 0. LanPM 定位（先读这段）

**LanPM = LAN + PM。** 名字里的两件事才是主轴：

| 轴 | 含义 | 产品重心 |
|----|------|----------|
| **LAN** | 无中心、局域网/VPN 发现与同步、数据不出域 | 群组内点对点协作底座 |
| **PM** | 项目管理：看板 / 任务树 / 甘特 / 驾驶舱等 | **用户打开软件要完成的工作** |

**聊天与文件不是目的，是为项目服务的手段：**

- 聊：围绕任务、群组、交付物沟通，不是做「局域网 QQ」  
- 文件：挂在项目/任务上下文里传与共享，不是做「局域网网盘/飞鸽传文件」  

因此与飞鸽、飞秋的差距 **主要是品类差距，不是单纯功能落后**：

| | 飞鸽 / 飞秋 | LanPM |
|--|-------------|--------|
| 品类 | 局域网 **即时通讯 / 传文件** | 局域网 **项目管理协作** |
| 第一生产力 | 消息送达、大文件续传 | **任务推进、项目可见性** |
| 聊天/文件 | 产品本体 | **附属能力**，够用即可 |
| 该不该追平断点续传、离线队列、投屏… | 他们的主战场 | **默认不追**；仅当「卡住项目协作」时再开 TASK |
| 信创 | 用全平台包卖 IM/传文件 | **客户含信创**；LanPM **天生跨平台**（Win/macOS/Linux · x64/ARM 同步规划），卖可部署的 LAN+PM |

下文 §2–§4 仍记录竞品功能（便于以后查）；**决策以本节为准**。

## 1. 飞鸽 / 飞秋共同定位（竞品侧）

| 维度 | 飞鸽传书 (IPMSG) | 飞秋 (FeiQ) |
|------|------------------|-------------|
| 场景 | 企业 / 学校 / 家庭局域网即时通讯 | 同左，偏「增强版飞鸽 + 类 QQ」 |
| 架构 | 无中心服务器，局域网直连 | 无中心服务器，兼容 IPMSG |
| 协议端口 | TCP/UDP（经典 2425；现代版另有 UDP/KCP 等） | 兼容飞鸽，同用 TCP/UDP **2425** |
| 核心卖点 | 高速传大文件 / 文件夹、断点·断网续传、跨网段、信创全平台 | 传文件快 + 群聊/分组/隐身/远程协助等社交办公能力 |
| 开源 | 经典 IPMSG 有开源血统；官网现推商业/信创发行版 | **不开源**，绿色免费 |

**可借用的 LAN 底座原则（仅底座，非产品目标）：**

1. **零服务器**：装上就能协作  
2. **数据不出网**：内网同步，安全可控  
3. **自动发现**：UDP 广播扫在线节点  

**不可借用的优先级：**「文件是第一生产力」——那是飞鸽/飞秋的；LanPM 的第一生产力是 **项目与任务**。

## 4. 飞鸽 vs 飞秋 · 对照

| 维度 | 飞鸽传书（现代 9.0） | 飞秋 |
|------|----------------------|------|
| 协议兼容 | IPMSG 系本家 | **兼容飞鸽**，可互通基础能力 |
| 文件续传 | 断点 + **断网续传**、文件夹续传、KCP/弱网 | 断点续传 + 秒传叙事 |
| 离线 | 9.0 系统化离线消息/图/文件 | 「离线自动发送」较早具备 |
| 群协作 | 讨论组 @、按成员离线 | 群聊/群共享/群日志更「QQ 化」 |
| 跨网段 / 防火墙 | 9.0 明确强化 | 多网段刷新好友 |
| 远程 | 增强版远程控制 / 投屏 | 远程协助 + 语音 |
| 平台 | Win / Mac / Linux 信创 / 移动 / 鸿蒙 | 以 Windows 经典客户端为主 |
| 政企 | 另有「联信」服务器版 | 企业应用 + 二次开发接口 |
| 差异化 | 信创全平台、弱网文件夹、投屏/终端/剪贴板 | 空间日志、应用管理器、日程、换肤、隐身分组 |

**一句话：**  
飞鸽把「传得稳、传得全平台、弱网也能续」做到极致；飞秋把「像 QQ 一样好用的局域网社交办公」做到极致。

## 5. 对 LanPM 的启示（以 PM + LAN 为准）

> **（已修订）** 不再把「追上飞鸽/飞秋 IM 能力」当作目标。差距在品类：他们卖通讯与传文件，我们卖 **局域网项目管理**。

### 5.1 真正要对齐的（LAN 底座 + 够用的协作管道）

| 能力 | 为何需要 | 备注 |
|------|----------|------|
| 无服务器 + 局域网发现 | **LAN** 轴 | 已有 UDP 发现 / 发现面板 |
| 数据不出域 | **LAN** 轴 | 产品原则 |
| 群组内成员在线 | 项目协作需要知道谁在 | 够用即可，不必做隐身/好友比较 |
| 围绕群组/任务的聊天 | **为项目服务** | 不是做全功能 IM |
| 项目上下文下的文件传收 | **为项目服务** | 进度可见即可；不与飞鸽拼续传军备 |

### 5.2 刻意不追的（飞鸽/飞秋主战场 · 原样搬）

| 能力 | 态度 |
|------|------|
| 断点 / 断网续传、KCP 弱网、文件夹海量小文件军备 | **默认不追军备**；交付物传失败成阻塞再评估（见 §6.2） |
| 离线消息/离线文件完整 IM 队列 | **不做 IM 离线**；项目数据离线补同步另论（task/chat sync、task_crdt） |
| 投屏 / 超级终端 / 便笺剪贴板 / 远程协助 | **核心不做** → **可购插件**（§6.3 · §7 · §8） |
| 语音 / 视频 | **核心不做** → **可购插件**（局域网会议见 §8.2） |
| 飞秋空间日志、应用管理器、日程、换肤、涂鸦、好友比较 | **不做** |
| 兼容 IPMSG 2425 互通 | **默认不做** |
| 飞鸽联信服务器版（有中心政企 IM） | **不做**（与无中心冲突） |
| 为追平飞鸽而堆「全 CPU 发行包数量」 | **不按竞品节奏追包**；跨平台多 arch 是默认交付面（§5.5） |

### 5.3 必须做强的（飞鸽飞秋没有、LanPM 才有）

| 方向 | 说明 |
|------|------|
| 看板 / 任务树 / 甘特 | **PM 本体**（永不插件化拆卖） |
| 驾驶舱 / AI 评估等 | 企业级项目视角；高级能力可插件/加购（§7） |
| 任务 ↔ 聊天 ↔ 文件 的关联 | **第一吸收重点**（§6.1） |
| 群组即项目边界 | 发现加入 = 进协作空间，而非「加好友」 |

### 5.4 体验原则

1. **先问：这件事是否推进项目？** 否 → 不进 Sprint / 最多进插件候选  
2. 聊天/文件以「任务上下文够用」为验收，不以「像飞秋」为验收  
3. LAN 发现与同步要稳——底座，不是 IM 功能清单  
4. 与飞鸽/飞秋的功能差 → **品类差异 / Out of scope**，不是 backlog 债  
5. 独立能力可插件化；**90% 免费 / 小众收费**（§7.0），勿把高频能力做成付费墙  
6. **Electron 更重**：功能与美观必须持续领先，否则轻量竞品碾压（§11）  

### 5.5 客户群体：含信创 · 天生跨平台

**信创是目标客户；跨平台是产品天性（非后期补丁）。**

| 层面 | 态度 |
|------|------|
| **谁用** | 政企、国企、信创办公网、国产 OS 机房等 **纳入客户群体** |
| **卖什么** | 仍是 **LAN + PM**，不是局域网飞鸽替代品 |
| **跑在哪** | **天生跨平台**：Windows · macOS · Linux（含统信 UOS、麒麟等） |
| **CPU 矩阵** | **x86_64 与 ARM（飞腾/鲲鹏等）同步规划**；龙芯等纳入同一路线图 |
| **与飞鸽差异** | 飞鸽用「信创全平台包」卖传文件 IM；LanPM 用「跨平台可部署的局域网项目管理」 |
| **工程含义** | Electron 多 arch、原生依赖进 CI/发版矩阵；禁止写死仅 Windows 假设 |
| **售卖/插件** | 内网可离线授权；**禁止**强制公网商店才能用核心或已购插件 |

**原则：**

1. **不追**飞鸽的信创 IM 功能军备  
2. **必须**跨平台（含信创 OS + 多 arch）与通用桌面同步规划  
3. 数据不出域、内网无强制外网依赖  

当前 `electron-builder.yml` 已有 win/mac/linux；后续显式补齐 **x64/arm64** 与统信/麒麟冒烟（§7）。

## 7. 插件化与可购买规划

> 飞秋有「应用管理器 / 二次开发接口」；LanPM 走 **免费主路径够用 + 小众能力可购**。  
> 文档：`docs/06` P1「插件系统」· P2「完整插件市场」；代码尚未落地。  
> **收费边界以 §7.0 / §10.0 为准**（不是「凡插件必收费」）。

### 7.0 免费 vs 收费（已拍板 · 2026-07-11）

| 规则 | 判定 | 商业结果 |
|------|------|----------|
| **≥约 90% 用户都会用到** / 项目主路径刚需 | 高频、强项目相关 | **必须免费**（进核心或免费模块，永不单卖卡脖子） |
| **仅少量用户 / 特定场景** 才需要 | 专业、小众、重资源 | **可收费**（可购插件 / 付费包） |

**推论：**

1. 分批次交付（§10）仍然成立——先做高频，再做小众。  
2. 第一波「日历 / 白板 / 基础验收」→ **免费交付**，不是付费「项目节奏包」。  
3. 第二波起偏专业能力（高级排程、完整会议 SFU、AI 周报等）→ **可购**。  
4. 「做成插件」≠「收费」：插件可以是**免费模块**（可卸载/可扩展），收费只针对小众包。

### 7.1 总原则

| 原则 | 说明 |
|------|------|
| **90% 免费** | 最常用核心与高频项目能力免费；见 §7.0 |
| **小众可购** | 特定少数用户需求 → 付费插件/SKU |
| 本体永不拆卖 | LAN 发现/同步、群组、看板、任务树、基础甘特、基础聊天与文件 |
| 独立可拔插 → 插件 | 便于扩展与可选安装；**免费插件与付费插件并存** |
| **弱化能力** | 可插件化；是否收费看是否小众（§6.3 · §10） |
| 内网可购 | 离线许可证；禁止强制公网才能用已购插件 |
| 同步类谨慎 | 未知类型兼容；会议类可旁路 SFU |
| 开源优先 | 能嵌库就嵌库（§8） |

### 7.3 必须免费（核心或免费模块 · 不可收费卡脖子）

**A. 永远核心**

- 无服务器发现与群组加入  
- 任务 / 看板 / 任务树 / 基础甘特与同步  
- 基础聊天（含 `/task`、基础 @）与项目上下文文件传收  
- 跨平台安装与数据不出域  

**B. 高频项目能力 · 免费（可插件形态，但不收费）— 见 §10.2**

- 任务日历视图  
- 协作白板（挂群组/任务）  
- 基础验收/检查清单（轻量表单）  

**C. 可收费（小众）— 见 §10.3～13.4**

- 高级排程（基线/关键路径/资源负荷）、完整局域网会议 SFU、AI 周报、重型知识库、深度互通等  

### 7.4 落地节奏

> **做什么：以 §10 为准**；**收费：以 §7.0 为准**（第一波免费，第二波起可购）。

| 阶段 | 内容 | 收费 |
|------|------|------|
| 现在 | PM 主线（§6.1 三角）；预留扩展点 | 免费 |
| P1 | **§10 第一波免费能力**：任务日历 → 白板 → 基础验收；可选插件加载器 | **免费** |
| P1～P2 | **§10 第二波可购**：高级排程、敏捷迭代、AI 周报 + **付费授权跑通** | **可购** |
| P2 | 会议包 / 轻知识库等（可购）+ **公开/内网插件市场**（安装·更新·付费） | **可购** + **M8** |

### 7.5 与吸收清单的关系

- §6.1（A*）→ **核心增强**  
- §6.2（B*）→ 核心或插件均可  
- §6.3 弱化表 → **仅插件（或永不）**  
- §6.4 护城河 → **永远核心**  
- 日历/白板/基础验收 → **免费模块**（可插件形态）；会议完整版 → **可购**（§7.0 · §10）  
- 大厂对齐增值 → **§9**（其中日历/白板/基础表单按 §7.0 免费）  
- **实际先做哪些** → **§10 精选短名单**（勿被全量目录带跑）  

### 7.6 架构注意：无中心 vs 会议 SFU

LanPM 本体是 **无中心 P2P**。多人音视频通常需要 **SFU/MCU**：

| 模式 | 做法 | 适用 |
|------|------|------|
| A. 旁路服务插件 | 群组内一台机器或内网小主机跑 LiveKit/Jitsi；客户端插件连接 | 正式「局域网会议」 |
| B. 小房间 mesh | WebRTC mesh（2～4 人），无独立 SFU | 轻量语音/投屏 POC |
| C. 外挂进程 | 调起 RustDesk 等独立客户端 | 远程协助，集成浅 |

**信创：** 旁路服务须可离线安装、数据不出公网；禁止默认连公有 meet.jit.si / LiveKit Cloud。

## 11. Electron 生存条件：功能与美观必须领先

> **不是「对抗」Rust/Tauri。**  
> 事实是：Electron **更重**（包体、内存、启动）。若功能上、美观上**没有明显领先**，用户会很快被 **Rust/Tauri 的轻量优势碾压**——同一套「局域网壳 + 聊天传文件」他们可以做得更省资源。  
> **因此：** 轻量是对方的结构性优势，我们赢不了「谁更轻」；必须在 **功能深度**、**视觉/交互质感** 上持续领先，并用 **公开/内网插件市场（付费可下载）** 形成生态锁定（§11.8），让用户愿意为体验付重量税。

### 11.1 竞争现实（认清牌面）

| 维度 | Electron（LanPM） | Rust / Tauri 同类 |
|------|-------------------|-------------------|
| 包体 / 内存 / 启动 | 偏重 | **天然领先** |
| 裸传文件 / 发现 / 管道 | 够用即可 | 往往更容易做快做稳 |
| 嵌 React + Yjs + 开源白板等 | 成熟 | **同样能做**（WebView） |
| 复杂 PM 多视图 + 企业 UI 抛光 | 生态与迭代快，**必须做出代差** | 能抄功能，难在短时间追上「一体+质感」 |
| 信创 Linux 复杂嵌入/预览 | Chromium 一致性相对稳 | 原生 WebView 碎片成本更高（可转化为我们的体验优势） |
| **插件市场（公开/内网）+ 付费分发** | JS/扩展生态成熟，易做加载·沙箱·热更新·授权 | **能做扩展点，难快速做成「可逛可买可更新」的市场**（见 §11.8） |

**若功能≈美观≈对方：** 用户会选轻的 → Electron 路线失败。  
**若功能明显更深、界面明显更高级：** 重量可被接受（对标 Discord/VS Code/Figma 桌面端逻辑）。

### 11.2 两条必须同时领先的轴

| 轴 | 含义 | LanPM 落点 | 失败信号 |
|----|------|------------|----------|
| **功能领先** | 不是多几个按钮，而是 **项目语义一体**：任务↔聊↔文件↔日历↔白板↔甘特↔驾驶舱同一真相源 | §6.1 · §10 · M1–M3 下表 | 「就是个重一点的飞鸽/聊天工具」 |
| **美观领先** | 第一眼与日常操作质感压过「能用的原型」；圆角、层级、动效、密度统一 | `.cursorGrowth/learn/UI优化.md` · `visual-polish-ux.md` · verify:visual | 「丑且卡，还占内存」 |

两条缺一：轻量竞品即可碾压。

### 11.3 功能领先：值得持续砸的深度（抄清单容易，抄一体难）

| ID | 能力 | 为何构成「愿意忍受 Electron 重量」的理由 |
|----|------|------------------------------------------|
| **M1** | 项目语义总线 | 任何协作对象落到任务；不是聊天室挂了个看板 |
| **M2** | 多视图 CRDT 一致 | 看板/树/甘特/驾驶舱不漂移；离线合并不炸 |
| **M3** | 跨项目驾驶舱 | 主管级价值；传文件工具天然不做 |
| **M4** | 信创上复杂预览/嵌入稳定 | 政企「能跑且好看」；把 WebView 碎片变成对方成本 |
| **M5** | 交付物 + 验收闭环 | 项目结果可归档、可验收 |
| **M6** | 小众专业可购包 | 排程/敏捷/会议等锁住工作流 |
| **M7** | 内网项目图 AI | 基于本群组任务图的周报/风险，非套壳聊天 |
| **M8** | **插件市场（公开 + 内网）** | 可发现、可下载、可付费、可更新；生态与收入飞轮（§11.8） |

> 这些不是为了「打败 Rust」，而是为了 **证明选 Electron 有回报**：同样重量下，只有我们把局域网 PM 做到这个深度与完整度，并带上**可扩展的付费生态**。

### 11.4 美观领先：与功能同级的硬要求

| 要求 | 说明 |
|------|------|
| 视觉 SSOT | 遵守 `UI优化.md`（Canvas / Surface / Card、圆角与阴影令牌） |
| 验收 | `verify:visual` 等门禁不降级；新功能不得引入「原型感拼接」 |
| 第一印象 | 打开即像成熟产品，而不是 Electron 默认灰框 |
| 密度与动效 | 协作密集界面仍清晰；动效服务层级，不噪声 |
| 跨平台一致 | Win/macOS/Linux（含信创）观感统一——这是相对碎片 WebView 的体验优势 |

**原则：** 功能 Sprint 若牺牲美观债，等于给轻量竞品送用户。

### 11.5 明确不要做的自我安慰

| 做法 | 为何无效 |
|------|----------|
| 跟 Tauri 比包体积/内存 | 结构性必输 |
| 只堆传文件速度军备 | 对方更易领先 |
| 功能平庸但「我们品牌是 Electron」 | 用户不在乎壳 |
| 美观落后却说「先功能后 UI」长期化 | 轻量竞品功能追上的瞬间被碾压 |

### 11.6 与 §10 分批的对齐

| 批次 | 对「功能+美观领先」的贡献 |
|------|---------------------------|
| 核心三角 + 第一波免费 | 功能：全员活在项目对象上；美观：日历/白板/验收也必须按 UI SSOT |
| 第二波可购 | 功能代差（排程/敏捷/AI）；付费也要配得上质感 |
| 信创矩阵 | 在重环境里仍稳、仍好看 → 体验优势 |
| **插件市场（P2）** | **M8**：公开店 + 内网私有源；付费下载/更新 → 生态锁定 |

### 11.7 一句话

> **Electron 不能靠「更轻」活，只能靠「明显更好用、明显更好看」，再加上「有得装、有得买」的插件市场。**  
> 功能深度 × 美观质感 × **插件生态（公开/内网付费分发）** = 用户容忍重量的理由；否则 Rust/Tauri 轻量优势会碾压过来。

### 11.8 差异点：公开 / 内网插件市场（付费可下载）

> **判断：** 单机「加载一个本地插件」Rust/Tauri 也能做；难的是做成 **市场**——目录、搜索、版本、签名、付费、更新、内网镜像。这是 Electron/JS 扩展生态更顺、且能形成飞轮的差异点（对齐 docs/06 P2「完整插件市场」）。

| 形态 | 谁用 | 要求 |
|------|------|------|
| **公开插件市场** | 通用客户 | 浏览/搜索、付费购买、下载安装、版本更新、签名校验、评价（可后置） |
| **内网 / 私有插件源** | 信创政企 | **不依赖公网**；企业镜像或局域网源；离线许可证；与 §7.0 内网可购一致 |

| 能力层 | 说明 | 相对 Rust 纯原生扩展的难度 |
|--------|------|---------------------------|
| 插件运行时 | UI 槽、任务只读 API、可选同步类型；免费/付费插件同一加载器 | 中（两边都能做） |
| **市场前端** | 商店页、详情、购买态、更新提示 | 中高（产品面） |
| **分发与更新** | 包格式、差分/整包更新、兼容宿主版本 | 高 |
| **付费与授权** | 购买 → 许可证绑定设备/群组；离线激活 | 高（且信创刚需） |
| **安全** | 签名、权限声明、沙箱；恶意插件治理 | 高 |
| **生态冷启动** | 先官方付费包填满货架，再开放受控第三方 | 高（时间与运营） |

**为何说 Rust「做市场更难」（准确表述）：**

1. **不是不可能**——Tauri 也可 iframe/侧载扩展；不要神话。  
2. **难在生态与产品复合：** JS 插件（React 组件、npm 依赖、与渲染进程同构）开发者池更大；官方付费包（排程/敏捷/AI/会议）可先用同一技术栈快速上架。  
3. **内网市场**要解决镜像、离线许可、无公网更新——这是产品+运维，和「写个 Rust dynlib」不是同一量级。  
4. **飞轮：** 市场货架越满 → 越难被「更轻但只有壳」的竞品替换（切换成本含已购插件）。

**落地节奏（与 §7.4 对齐）：**

| 阶段 | 市场相关交付 |
|------|----------------|
| P1 | 插件加载器 + 官方包侧载；付费授权 POC（可无商店 UI） |
| P2 | **商店 UI** + 公开源（可先官方 only）+ **内网私有源** + 安装/更新 |
| 后 | 受控第三方上架、评价与分成 |

**原则：** 市场是 **M8 战略差异**，但排在功能/美观领先之后——空壳商店救不了平庸产品；有深度后再用市场放大。
