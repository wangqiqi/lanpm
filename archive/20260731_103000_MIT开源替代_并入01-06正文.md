# MIT 开源替代对照

> **最高目标：完成产品。**  
> **选型铁律**：有社区稳定、无传染的开源（优先 **MIT**；Apache-2.0 / BSD / ISC 同等）→ **用开源**；可按本系统/项目**修改与适配**；不能开箱即用的放入 **`3rd/`**。  
> **自研仅当**：无同类功能，**或**同类功能明显不适应——并须写清理由。  
> 事实来源：`docs/01`–`06`、`package.json`、`src/`。大范围替换立项走 `/plan`。

---

## 0. 默认决策（先读这节）

```
目标：尽快、稳定地完成产品能力
        │
        ▼
有社区稳定 MIT（或同等宽松）同类实现？
  ├─ 无 → 自研（登记理由）
  └─ 有 → 能否直接 npm/依赖使用？
        ├─ 能 → 依赖接入 + 薄适配（IPC/协议胶水）
        └─ 不能开箱即用（要改源码/裁剪/钉版本）
              → 放入 3rd/ 修改适配（保留上游 LICENSE + ORIGIN.md）
                    │
                    ▼
              改完仍不适应产品约束？
                ├─ 是 → 才允许自研（登记「为何开源不适应」）
                └─ 否 → 用改编后的开源，禁止推倒重写
```

| 优先做 | 最后才做 |
|--------|----------|
| npm 开源依赖 · `3rd/` 改编开源 · 薄适配层 | **自研**（无同类 / 同类不适应） |

| 该用开源（含改编） | 才允许自研 |
|--------------------|------------|
| UI、拖拽、甘特、高亮、PDF、搜索、虚拟列表、i18n、WebRTC 封装、CRDT 引擎、加密库、表情、Markdown、图表… | 确认无同类，或同类无法满足：无中心协议面、群组三类、Stub/真网统一传输、不出域胶水等 |

**「不适应」须具体**：无中心、数据不出域、Stub 联调、信创、体积/性能硬约束等——禁止只写「我们更熟 / 重写更爽」。

**评审口令**（答不上来 → 改选型）：

1. 社区有没有同类 MIT（宽松）实现？  
2. 不能开箱即用时，能否 **改一改 / 放进 `3rd/`** 就够用？  
3. 为什么必须自研？（无同类 / 不适应的具体点）  
4. 这条路径是否更快完成产品？

## 0.1 `3rd/` 目录约定

存放**非开箱即用**、需在本仓库内修改/裁剪/钉死的开源组件与模块（vendor / fork 快照）。

| 规则 | 说明 |
|------|------|
| 路径 | 仓库根目录 `3rd/<name>/` |
| 何时用 | 要改源码、裁剪子系统、钉 commit，或不宜只靠 npm |
| 何时不用 | 能 `package.json` 直接依赖且无需改源码 → **不要**进 `3rd/` |
| 必含 | 上游 `LICENSE`（或副本）· `ORIGIN.md`（上游 URL、版本/commit、本仓改动摘要、授权） |
| 授权 | 仅 MIT/BSD/Apache/ISC 等无传染；**禁止** GPL 族进 `3rd/` 当库 |
| 引用 | `file:` / workspace / 构建别名；业务侧禁止再复制一份「伪自研」 |
| 回馈 | 通用修复尽量上游 PR；LanPM 特化留在 `3rd/` diff，并在 `ORIGIN.md` 写清 |

说明文件：[`3rd/README.md`](../3rd/README.md)。

## 1. 授权口径

| 类别 | 可否依赖 / 进 `3rd/` | 说明 |
|------|----------------------|------|
| **MIT / BSD / ISC / Apache-2.0 / Unlicense** | ✅ **默认选用** | 无传染；允许修改适配 |
| **MPL-2.0** | ⚠️ 慎用 | 改动文件需开源；外挂另论 |
| **LGPL** | ⚠️ 慎用 | 子进程/动态链接通常可接受，捆绑需合规 |
| **GPL / AGPL（依赖）** | ❌ 禁止 | 传染风险 |
| **专有 / Commons Clause** | ❌ | 不符合目标 |

**当前 npm 直依**：几乎全 MIT；`highlight.js` 为 BSD-3-Clause。  
**外挂例外**：LibreOffice 见 §5。

## 2. 早期为何自研多？今后怎么纠偏？

### 2.1 历史原因（不是继续自研的借口）

早期无「无中心 LAN + 完整 PM」同构成品，壳/UI 用 Electron/React/Ant、协议自研——合理。  
通用能力未优先「开源 / `3rd/` 改编」→ **债务**，按 §6 还。

### 2.2 自研前提：无同类，或不适应

| 仍可能自研 | 前提 |
|------------|------|
| 同步报文 / `NetworkTransport` | 无同构；或开源强绑中心服不适应 |
| 群组三类 + 匿名规则 | 产品语义，无现成库 |
| 任务/文件与群组编排 | 胶水；底层仍用 Yjs/SQLite 等开源 |

### 2.3 盲目自研的坏处

耽误产品交付 · 更不稳定 · 难维护。  
**纠偏顺序**：开源依赖 → 适配/`3rd/` → 最后自研。

## 7. 维护规则

- 新功能：先开源 → 再 `3rd/` 改编 → 最后自研；**以完成产品为准**。
- 进 `3rd/`：必须有 `LICENSE` + `ORIGIN.md`；授权无传染。
- 新增 npm：MIT/BSD/Apache；扫传递依赖无 GPL 族。
- 状态以 `docs/06_ROADMAP` / `docs/01` §1.3.1 为准。
- 债务项 Sprint 的 Done when：已用开源或 `3rd/` + verify。

---

## 8. 一句话结论

**完成产品优先。** 有同类开源就用；可改、可进 `3rd/`。  
**自研 = 无同类，或同类确实不适应**——不是默认选项。
